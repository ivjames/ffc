# Screen inventory (the focused reader)

The design docs (`public/docs/style-guide.html` + `screens.html`, generated by
`scripts/build-style-guide.py` + `scripts/build-screens-sheet.py`) encode
claims about screen structure. They drift from the app, and redrawing a page
from memory produces subtly wrong docs — the recurring failure modes are
misplaced elements (a result shown in-card drawn as a standalone banner),
wrong vertical ordering, buttons drawn in a row that are actually stacked, and
conditional blocks drawn as always-present. The fix is to never draw from
memory: read the component through a focused reader first, then edit the
builder to match what it reports.

## Process

1. **Map the screen to its component.** Routes live in `src/App.tsx`
   (namespaced under /golf, /arcade, /me; legacy paths redirect). Doc page
   numbers are the `SCREENS` order in the builders.
2. **Dispatch readers.** Use the Agent tool with `subagent_type: Explore`,
   batching 3–4 component files per reader; launch batches in parallel, in the
   background. Use the prompt template below verbatim, filling in the files.
3. **Reconcile the docs.** Edit the *builders* (never the generated HTML) to
   match the report. Conditional blocks — anything the reader says renders
   only when populated — get the dashed-outline treatment (`border=DASH` in
   the sheet, `cond` class in the guide); always-present elements stay solid.
4. **Verify by rendering, not by rebuilding.** Regenerate both docs, then
   screenshot the changed board and look at it (recipe below). A clean build
   proves nothing about layout.

## Reader prompt template

> Read these React screen components and produce a precise structural
> inventory of each — I'm comparing them against a wireframe doc, so I need
> the CURRENT layout as built.
>
> Files: <list absolute paths>
>
> For EACH screen report, concisely:
> - Top bar: title text, back target, right-side controls. Describe shared
>   chrome (TopBar / HeaderControls) only from files you actually read this
>   run — say "the global header control" rather than guessing its contents
> - Main content elements IN VERTICAL ORDER, each as a short line, quoting
>   the ACTUAL label/heading strings from the JSX
> - WHERE each message/banner renders — inside which container. If a result,
>   error, or badge renders inside a card/row, say so explicitly; never let
>   "there is a banner" pass without saying what it's inside of
> - For button groups: stacked column or horizontal row?
> - Interactive controls and their states (empty / error / loading /
>   selected / gated / signed-out), and which blocks are CONDITIONAL —
>   rendered only when populated
> - Repeated rows: the anatomy of one row
> - Whether the layout scales per player (1–4)
>
> Be factual and specific. Tight bulleted list per screen. Do not propose
> changes; just report what's there.

## Screenshot-verify recipe

Global playwright lives outside the repo; run from its directory. The HTML
path is resolved from the current checkout (never hardcode it):

```bash
DOC="$(git -C "$(pwd)" rev-parse --show-toplevel)/public/docs/screens.html" \
bash -c 'cd /opt/node2*/lib/node_modules/playwright 2>/dev/null || cd $(npm root -g)/playwright; node -e "
const { chromium } = require(\"playwright\");
(async () => {
  const b = await chromium.launch({ executablePath: \"/opt/pw-browsers/chromium\" });
  const p = await b.newPage({ viewport: { width: 900, height: 1300 }, deviceScaleFactor: 2 });
  await p.goto(\"file://\" + process.env.DOC);
  // .cell = one artboard on the contact sheet; .page.sp = one guide page
  await p.locator(\".cell\").nth(IDX).screenshot({ path: \"OUT.png\" });
  await b.close();
})().catch(e => { console.error(e); process.exit(1); });
"'
```

If `/opt/pw-browsers/chromium` doesn't exist in your environment, drop the
`executablePath` option and let Playwright find its own browser.

Then Read the PNG and check it against the reader's report before committing.
